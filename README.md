# мини-CRM «Объекты и задачи»

Руководитель ставит задачи по объектам, исполнители берут их в работу и сдают
на проверку. Права разграничены на уровне базы: правила действуют и тогда,
когда к Supabase обращаются напрямую, мимо интерфейса.

Стек: React 19 + TypeScript + Vite, Supabase (Postgres, Auth, RLS).

## Запуск

```bash
npm install
cp .env.example .env     # заполнить своими значениями
npm run dev
```

### Переменные окружения

| Переменная | Где взять | Куда попадает |
|---|---|---|
| `VITE_SUPABASE_URL` | Supabase → Settings → API Keys | в браузер |
| `VITE_SUPABASE_ANON_KEY` | там же, `publishable` | в браузер |
| `SUPABASE_SERVICE_ROLE_KEY` | там же, `secret` | только локальные скрипты |

Первые две переменные публичны по своей природе: они уходят в браузер, и это
нормально, потому что доступ к данным решают политики RLS, а не знание ключа.
Третья — секрет, нужна только для создания пользователей и тестовых данных.
Файл `.env` в `.gitignore` и в репозиторий не попадает.

### База

Миграция одна: `supabase/migrations/0001_init.sql`. Применить можно через
Supabase CLI или вставив её содержимое в SQL Editor проекта.

### Тестовые данные

```bash
npm run seed
```

Создаёт трёх пользователей, три объекта и шесть задач во всех статусах,
прогоняя их через те же проверки, что работают в приложении.
Скрипт можно запускать повторно, он сам чистит прошлые данные.

| Роль | Логин | Пароль |
|---|---|---|
| Постановщик | `manager@example.com` | `Test1234!` |
| Исполнитель | `worker1@example.com` | `Test1234!` |
| Исполнитель | `worker2@example.com` | `Test1234!` |

### Проверка защиты

```bash
npm run security-check
```

18 попыток обойти правила в обход интерфейса: прочитать чужую задачу, сменить
статус напрямую, подделать историю, повысить себе роль. Все должны получить отказ.

## Как устроена защита

**1. Данные закрыты политиками RLS, а не интерфейсом.**
На всех таблицах включён Row Level Security. Исполнитель видит только задачи,
где он назначен, и только те объекты, где у него есть хотя бы одна задача.
Запрос мимо приложения вернёт ему тот же урезанный набор.

**2. Статус меняется только функцией `change_task_status()`.**
Она проверяет роль, назначение исполнителя, допустимость перехода и
обязательность комментария. Прямой `UPDATE` колонки `status` блокирует триггер
`tasks_guard_status` — даже у служебного ключа с полными правами.

**3. Допустимые переходы лежат в таблице, а не в коде.**
`status_transitions` — единственный источник правды. По ней работает и функция
смены статуса, и интерфейс, который рисует кнопки. Разойтись они не могут.

**4. История пишется базой и неизменяема.**
Запись создаёт триггер при создании задачи и функция при каждой смене статуса.
Прямые `INSERT`, `UPDATE` и `DELETE` в `task_history` запрещены триггером
`task_history_immutable`. Единственное исключение — удаление каскадом вместе с
самой задачей.

**5. Роли нельзя поменять из приложения.**
У таблицы `profiles` нет политик на запись вообще: ни один клиент не может
создать профиль или сменить себе роль.

**6. Регистрация закрыта.**
Пользователей заводит администратор. В приложении есть только форма входа.

## Структура

```
src/
  lib/
    supabase.ts   клиент Supabase
    auth.tsx      сессия, профиль, вход и выход
    types.ts      типы и подписи статусов
  pages/
    Login.tsx       вход
    Objects.tsx     список объектов
    ObjectCard.tsx  карточка объекта со списком задач
    TaskCard.tsx    карточка задачи: данные, действия, история
    MyTasks.tsx     «Мои задачи» для исполнителя
supabase/
  migrations/0001_init.sql   схема, политики, триггеры
scripts/
  seed.mjs             тестовые данные
  security-check.mjs   проверка защиты
```
